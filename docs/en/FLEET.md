PW Agent v0.6 adds a database-backed fleet layer on top of the v0.5 single-device architecture.

## Fleet registry

Each router is registered with a Device ID, display name, group, location, tags, enabled state, last-seen metadata, Agent version and an encrypted Device Secret.

The permanent Device Secret is encrypted before storage using an instance key generated by setup.

## Device picker

Telegram /start shows the active router and exposes Fleet / Devices. Selecting another device changes the active target for subsequent Telegram actions.

The Mini App Dashboard also provides fleet selection and metadata management.

## Zero-touch provisioning

Owners and Admins can add another router from Telegram or Dashboard.

PW Agent creates:

1. a new Device ID;
2. a random Device Secret;
3. an encrypted registry entry;
4. a single-use provisioning token valid for 30 minutes;
5. an OpenWrt install command.

The permanent Device Secret is never placed in the installation command.

## Groups, tags and location

Routers can be organized using groups such as Home, Office, Lab or Customers, arbitrary tags and a short location label.

These values are fleet metadata and do not alter OpenWrt configuration.

## RBAC

| Role | Typical access |
|---|---|
| Owner | Full platform access |
| Admin | Broad operational management inside its Device Scope; RBAC is read-only |
| Operator | Day-to-day operations without sensitive admin capabilities |
| Viewer | Read-only monitoring/status access |

Operator and Viewer accounts can be restricted to specific Device IDs.

Sensitive permissions include Terminal, Backup Restore, Agent Update, Rollback and alert/schedule management. RBAC mutation is Owner-only to prevent scoped administrators from escalating their own access.

## Audit log

Every queued command records user, source, device, action, redacted parameters, status, result summary and timestamps.

Sensitive values such as passwords, node links, subscription URLs, backup payloads and Terminal payloads are redacted.

## Config history and rollback

For supported UCI mutations, the Agent captures the affected /etc/config file before the operation.

The pre-change snapshot is encrypted on the router with a random router-only 32-byte key stored at `/etc/pw-agent/history.key`. The backend stores ciphertext only and does not receive this history key during normal operation. The visible diff contains changed UCI key names, not configuration values.

Owners and Admins can queue a rollback from Telegram or Dashboard.

## Advanced monitoring

v0.6 heartbeat data includes CPU percentage, memory percentage, WAN state, WAN IP, RX/TX counters, Passwall2 state, uptime and load.

The Dashboard summarizes heartbeat coverage for 24h, 7d and 30d, traffic deltas, WAN IP changes and Failover activity.

## Alert rules

Supported metrics include CPU, memory, load, WAN-down and Passwall2-down conditions. Rules include an operator, threshold, breach duration, cooldown, enabled state and destination chat.

## Maintenance mode

Maintenance mode temporarily suppresses operational alerts and pauses scheduled actions for that device.

## Scheduled actions

Schedule types:

- one-time
- interval
- daily
- weekly

The scheduling engine runs from the same one-minute cron used by Monitoring. Only explicitly allowed actions can be scheduled.

Examples include Passwall2 restart, subscription update, backup, router reboot, Agent update and Failover run.

Scheduled commands still pass through RBAC, queue leasing, idempotency and audit logging.

## Mini App Dashboard

The Dashboard includes Fleet selection, device metadata/groups, Monitoring, Router Operations, Command History, Audit and Rollback, Alert Rules, Maintenance, Scheduled Actions, RBAC management and access to the SSH Console.

All Dashboard API requests validate Telegram Mini App initData.
